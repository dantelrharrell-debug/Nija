# NIJA 12-round Trading IQ — IONOS integration handoff (review-only)

**Status:** PREPARATION ONLY. This document is not a deployment, an implemented payment API, or an authorization to enable Stripe. The canonical 12-round IONOS source is not contained in this repository. The existing six-round app under this directory and five-round Render billing module are DIFFERENT products and must not be silently treated as the IONOS game.

## Product contract
- One unified educational product: twelve fictional rounds **free to play**; optional one-time USD $1 unlock of personalized feedback for **eligible adults age 18+ only**. A visitor who does not buy does not generate $1 revenue.
- The paid results belong to the completed twelve-round run; reopen without a second charge for the permitted entitlement lifetime.
- All transaction amounts, pricing identity, eligibility, report authority and scoring must be enforced on a server with durable storage. No real-money trade, brokerage calls, lotteries, prize draws, live performance claims or customer orders.
- Under-13 Academy programming remains free of this game promotion; ages 13–17 may use approved educational content without payment solicitation. Obtain legal review of parental/age wording before launch.
- Preserve NIJA's existing $99 Trading Foundations checkout, customer records, application timestamps, consent data and trading authorization.

## Files added for review
- server/tiq12-contract.mjs: **pure** private manifest/answer/receipt validators. Provides version-pinned twelve-round scoring and rejects missing buyer proof, inappropriate age declarations, wrong offer or environment, unverified/returned/disputed purchases and malformed answers.
- tests/tiq12-contract.test.mjs: deterministic tests using fictional scenarios and fake payment objects. The test manifest is **not** the IONOS canonical game content.

These functions are **not** wired into server/index.mjs or billing_service.py, and they **must not** be imported into public/scenarios.js, public/app.js or a browser bundle. This deliberate separation avoids changing the currently merged six-round experience or switching on payment under a mismatched configuration.

### Private paid-score guard (review branch, not deployed)

The previously standalone `scorePurchasedTiq12(manifest, storedRun)` helper could compute a paid score from an adult-completed run without being passed evidence of a verified entitlement. The review-only fix now requires `scorePurchasedTiq12(manifest, storedRun, entitlement, offer)`. The `requireVerifiedTiq12Entitlement` validator rejects missing, mismatched, unpaid, unpersisted, live-mode, reversed, revoked, expired or unverified test-mode grants before invoking the existing canonical score calculation. Regression tests use fictional grants; no real payment is represented.

**Important trust boundary:** fields such as `persisted`, `providerVerified`, and `webhookSignatureVerified` are *assertions made by trusted backend code*, not cryptographic proof by themselves. The future backend must load both the run and entitlement from a private, durable store after authentication, validate a signed Stripe raw-body webhook and a fresh reconciled Stripe purchase, and atomically record event and entitlement provenance. Never use client JSON, localStorage, a Checkout success URL, an unverified event body, or a browser-supplied grant as the entitlement. The scoring guard alone does **not** implement the database, payment webhook, API, IONOS integration or complete Upgrade 6.

A grant is additionally restricted to the dedicated Stripe **test-mode** USD 100-cent price/product, matching run ID, manifest digest, owner proof hash, valid Checkout Session/Event IDs, explicit unreversed status, and an unexpired server-approved grant window. Live purchases require a separate independently reviewed design and are not enabled by this code.

### Exact isolated staging storage proposal (NOT applied or authorized)

A new **review-only**, additive **SQLite** schema is included at `server/tiq12-storage.schema.sql`, with synthetic Python integrity tests at `tests/test_tiq12_storage.py`. CI invokes those tests; they are not a provider database migration. The schema creates namespaced tables for completed adult-owned runs, one durable idempotent Checkout reservation per run, immutable Stripe event IDs, paid payment reconciliations, revocations, and report entitlements. It has no contact details, raw owner receipt, card information, Stripe secret or real customer record. It cannot make IONOS preview storage safe or accessible.

The proposal intentionally **persists a completed 12-round run only after an adult opts into the optional paid report**. The free game can run entirely in the browser. On opt-in, a future single authenticated `POST /game/runs/complete` must create a run ID and private HttpOnly browser receipt while validating all 12 answers against the canonical server-owned manifest; it must never accept a browser score. The persistence boundary must remain private to a paid, durable, dedicated backend with an approved origin, separate environment and reviewed retention policy.

**Read/grant mapping:** A server-only joined read of `tiq12_runs`, `tiq12_checkout_reservations`, `tiq12_verified_payments`, `tiq12_webhook_events`, `tiq12_revocations`, and `tiq12_report_entitlements` may construct the `requireVerifiedTiq12Entitlement` input. The `persisted`, `webhookSignatureVerified`, `providerVerified`, `refunded`, and `disputed` fields must be determined exclusively from trusted signed-webhook/Stripe reconciliation and persisted state, never a user-supplied JSON object. Before report access, additionally authenticate the buyer using a first-party receipt and obtain a fresh Stripe reversal check. SQLite CHECKs and triggers are only defense in depth: **they do not authenticate webhook signatures, establish provenance, or implement the HTTP API**. The table-level grant expiry must be checked against real server time; the provisional twelve-month report lifetime requires legal/product approval.

**Payment ordering:** Create and commit the one-per-run reservation with a fixed Stripe idempotency key **before** contacting Stripe. Reuse that key for a lost response, never generate a second Checkout for the same run; stop after the approved uncertainty window. On an authenticated raw-body signed webhook, reconcile current Stripe Price/Product, Session, Intent, Charge and refund/dispute state, then atomically insert immutable event, verified payment and grant or revocation. A duplicate event ID is ignored only after verifying the original durable result. A reversal received before a delayed completion is sticky; a refund or dispute after granting revokes future report access in the same transaction. Keep backups off-host, restrict to one writer and rehearse restart/restore. Do not execute this schema against existing NIJA customer, Academy, billing or trading storage.

`matchesTiq12WebhookPaymentSnapshot` now allows server-side Stripe reconciliation **without** acquiring the private browser owner proof: it compares stored owner proof **hashes** and exact run/manifest/charge identities. The separate `matchesVerifiedTiq12Payment` path still requires the original browser proof for report ownership. Neither helper verifies a Stripe signature, processes an event, writes a database, or is connected to a public endpoint.

**Deployment gates:** exact approved Render plan and explicit cost approval; workspace billing restored; a private persistent mount with approved ownership/fsync/backup; canonical IONOS export/scoring parity; restricted Stripe **test-only** key and *distinct* signed webhook secret installed by the operator through protected provider settings (never in chat/Git); verified hosted Checkout → webhook → reopened report → refund/dispute tests and accessibility review. The existing `game_sandbox/render.staging.yaml` is a DIFFERENT **72-decision** product and is not an approved deployment for this 12-round schema.

## Minimum approved backend operations (not implemented in this PR)
1. **POST /game/runs/complete**: after an adult explicitly opts into the optional $1 report, create a cryptographically unique, durable completed run and HttpOnly first-party ownership receipt in one transaction; validate the 12 ordered choices against the private canonical scoring manifest; bind age declaration, consent, original version/digest and abuse controls. Do not use email as ownership, and do not persist free-playing minors or create paid runs before an adult opts in.
2. **POST /game/checkout**: require completed adult-owned run; idempotently create a Stripe Checkout Session with **fixed 100-cent USD one-time price** in that environment, signed/opaque run reference and hashed ownership proof. Verify the configured active Stripe Price/Product and attach server-controlled metadata; never embed Stripe secrets or pass calculated scores from the client. Use the latest supported Checkout Sessions integration and dynamic payment methods.
3. **POST /game/stripe/webhook**: use raw request body and Stripe signature verification; persist event IDs uniquely and reconcile checkout.session.completed, checkout.session.async_payment_succeeded / async_payment_failed, refunds, disputes and related reversals. Fulfill only once against the verified paid session, exact line item, amount, currency, mode and buyer/run ownership. Return 2xx to retries only after durable commit; never grant access on success URL alone.
4. **GET /game/report/:runId**: require authenticated browser/account ownership, durable verified entitlement and current refund/dispute status; compute the private report from persisted canonical answers and the matching manifest. Permit authenticated reopening without charging twice for the approved retention period; support receipt recovery or customer support for lost-device access.
5. **GET /game/admin/analytics**: enforce server-side admin access and consent, unique visitor and event deduplication; calculate revenue only from authoritative paid transactions less refunds, fees and documented costs. Emit UNVERIFIED when data is incomplete.
6. Durable storage with additive isolated tables for game_runs, checkout_attempts, stripe_events, verified_payments, report_entitlements, analytics_events. Require unique keys, database transactions, integrity constraints, private access, backups and rollback before any migration.
